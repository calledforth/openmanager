How composer model settings are cached

OpenManager vs .tmp/t3code: where model catalogs, effort levels, and remembered selections live — and why Cursor is the hard case.

Bottom line

Verdict

OpenManager caches user selections well (model / mode / effort per workspace+provider in electron-store + Convex), but does not warm-boot a full provider model catalog for Cursor. Claude gets models from probe handshake; Cursor only gets models after a real session (or from a previously persisted profile).

t3code solves the boot problem with a disk snapshot of the full provider status — including per-model capability descriptors (effort, etc.) — then refreshes in the background. That is the pattern we are missing.

Desired (user intent)

What the composer shows / wants. Durable. Survives restarts.

Applied (agent truth)

What this process reported over the wire. Ephemeral. Never trust Cursor’s on-disk leftovers.

OpenManager — how it works today

Two different caches (easy to confuse)

  1. Composer preference cache — selected model, mode, effort, other config values. Persisted.
  2. Applied config cache — live ACP configOptions for one session/process (AppliedConfigCache). Intentionally not persisted.
  3. Provider profile / catalog — available models + capability flags like effortLevels. Persisted after a live session reports them; Claude can also fill this at probe time.

Data flow

App boot
  → electron-store restores profiles + workspace preferences
  → Convex subs merge cross-device profiles/preferences
  → AgentHost probes providers
       Claude  → handshake exposes catalog immediately
       Cursor  → probe exposes health/auth only (no model list)
  → renderer refreshes agent:providers
  → composer resolves models:
       live session → chrome/event → provider metadata/profile

User picks model / effort
  → React state updates
  → workspace preference → electron-store + Convex
  → on next session start, desiredConfig is reapplied
  → AppliedConfigCache seeds from session/new|load
  → unchanged values cost 0 RPCs thereafter

Composer preference schema

workspace_composer_preferences {
  workspacePath
  providerId
  modelId?
  modeId?
  configValues?   // e.g. { effort: "high", fast_mode: true, ... }
  updatedAt
}
// key conceptually: `${workspacePath}::${providerId}`

provider_profiles {
  providerId
  availableModels?: [{
    modelId, name, description?,
    effortLevels?, supportsFastMode?, supportsAutoMode?, ...
  }]
  availableModes?
  defaultModelId?, defaultModeId?
  updatedAt
}

How the composer resolves models / effort

From MessageInput.tsx — precedence and capability lookup are deliberately split so the effort pill does not blink when sources swap.

  1. Live/draft runtime availableModels
  2. Chrome / event projection
  3. Provider metadata / persisted profile

Effort levels come from the selected model’s effortLevels. Effort value comes from live configOptions first, else remembered configValues.effort.

Important design note

AppliedConfigCache must stay process-scoped. Cursor’s model state is process-global and persisted on disk by Cursor itself. A fresh spawn was measured reporting a model set by an already-exited process. Only wire responses from this connection are trusted. See docs/session-runtime-design.md §3–4.

t3code — how the reference does it

Core idea

Treat the provider status snapshot as the catalog cache boundary. One JSON file per provider instance includes models and normalized capability descriptors (effort / reasoning, context, fast mode, thinking).

Data flow

Cursor ACP  cursor/list_available_models
  → { slug, name, per-model configOptions }
  → normalize into ModelCapabilities.optionDescriptors
  → ServerProvider.models[] snapshot
  → in-memory managed-provider Ref
  → ProviderRegistry aggregate
  → disk: <baseDir>/caches/<instanceId>.json
  → server config / API → web model picker

User changes effort / etc.
  → ModelSelection.options: [{ id, value }]
  → composer draft Zustand + localStorage
  → dispatch selection to server
  → ACP session: setModel(), then setConfigOption()

Disk cache

Path: <baseDir>/caches/<instanceId>.json (e.g. caches/cursor.json for the default Cursor instance). 

{
  instanceId, driver, enabled, installed, version,
  status, auth, checkedAt,
  models: [{
    slug, name, isCustom, isDefault?,
    capabilities: {
      optionDescriptors: [
        { id: "reasoning", type: "select", options: [...], ... },
        { id: "fastMode", type: "boolean", ... }
      ]
    } | null
  }],
  slashCommands, skills, ...
}

Warm boot behavior

  1. Registry starts with cheap fallback snapshots
  2. Reads disk cache per instance
  3. Hydrates models + capabilities immediately → UI has a full picker
  4. Background forced health refresh re-discovers (Cursor calls cursor/list_available_models again)
  5. Merge logic keeps previous models/capabilities if refresh returns empty or strips capabilities
What they optimize for

Responsive boot (no blank picker), not “never rediscover.” Discovery still runs in the background; the disk snapshot bridges the gap.

Selection vs catalog separation

Concern Where
Catalog + capabilities Server disk snapshot + memory
User selection (model + option values) Composer draft store (t3code:composer-drafts:v1)
Live ACP option IDs Resolved against the active session before setConfigOption

Cursor raw ACP options are normalized at the boundary (effort → reasoning, context → contextWindow, etc.). The UI persists portable IDs; protocol-specific IDs are re-resolved live.

The Cursor model-settings cache bug surface

Bug / gap (research finding)

Cursor model details (catalog + effort/options) are not reliably available at provider boot. The app either waits for a live session, or leans on a previously projected profile that may be incomplete/stale. That is why “we can’t keep loading model details / effort when booting the provider” is painful today — there is no dedicated warm catalog cache like t3code’s.

Concrete failure modes

  1. Cold Cursor first use — modelsByProvider empty; picker has no rows until session/new or session/load publishes models.
  2. listModels dead path — AcpProbeRuntimeImpl.listModels() can spawn a temp session and return models, but nothing in production calls it during boot.
  3. Capability blink / missing effort pill — chrome / older profiles may carry id+name without effortLevels. MessageInput already tries to paper over this by looking up capabilities separately from the display list — which is a symptom that catalog sources disagree.
  4. Stale profile retention — projector only upserts availableModels when the new array is non-empty. An intentionally empty/changed catalog after a CLI upgrade will not clear the old Convex/electron profile.
  5. Effort remembered per workspace+provider, not per model — switching models can leave a remembered effort that the new model does not advertise. Runtime skips unsupported values; UI can still show a temporary mismatch until live options arrive.
  6. Do not “fix” applied Cursor settings — Cursor on-disk / process-global state lies across respawns. Persisting AppliedConfigCache would reintroduce the measured stale-model bug (respawn inheriting another process’s model). Desired prefs are fine; applied wire state is not.

Related measured Cursor costs (why cache matters)

  • session/set_model ≈ 2.9s even when unchanged, returns {}
  • session/set_config_option ≈ 1.4–3.0s, but returns full options (cacheable)
  • Unknown option on wrong model ≈ 1.4s then error
  • Steady state with a seeded applied cache: 0 RPCs per message

Source: docs/session-runtime-design.md, AppliedConfigCache.ts comments.

What this implies (still research — no changes)

  1. Keep desired vs applied split. OpenManager already got this right for session writes. Do not persist applied Cursor wire state.
  2. Add a warm provider-catalog cache for Cursor (t3code-style): snapshot models + effort/option descriptors to disk (or strengthen Convex/electron profile into a true boot hydrate), serve immediately, refresh asynchronously.
  3. Discover without opening a user session — either wire listModels into boot, or prefer Cursor’s cursor/list_available_models extension like t3code.
  4. Preserve on empty refresh. Never clobber a known catalog with [] from a failed/partial probe.
  5. Normalize capabilities at the boundary if Cursor option IDs keep shifting — store portable descriptors, re-resolve against the live session before writes.
